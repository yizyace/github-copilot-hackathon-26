## Coupling Issues
- **Tight Coupling — API Key Retrieval Inside Business Logic** in `pattern-buddy/src/claudeCaller.ts` (lines 1–93, PR #5): The `callClaude` function reaches directly into `core.getInput()` and `process.env.ANTHROPIC_API_KEY` to resolve its API key. This couples the Claude calling logic to the GitHub Actions runtime environment. The function can't be called from a test without mocking the Actions core module or setting specific environment variables.
- **Tight Coupling — GitHub Actions Runtime Inside Business Logic** in `pattern-buddy/src/commentPoster.ts` (lines 31–31, PR #6): This one's a recurring theme in this codebase. The `postComments` function reaches directly into `core.getInput('github-token')` to resolve its Octokit client — exactly the same coupling pattern previously flagged in `claudeCaller.ts`. The function is welded to the GitHub Actions runtime: you can't call it in a unit test without mocking `@actions/core`, and you can't reuse it outside of an Actions context without surgery. The new `buildSummaryComment` helper is nicely pure and decoupled by contrast, which highlights the inconsistency. Recurring pattern — also observed in Tight Coupling — API Key Retrieval Inside Business Logic in `pattern-buddy/src/claudeCaller.ts` (lines 1–93, PR #5).
- **DOM Manipulation Inside Business Logic** in `src/lib/soulStack/exportZip.ts` (lines 1–20, PR #7): The `downloadSoulZip` function is doing two genuinely separate things: (1) serializing the SoulStack into a zip archive, and (2) triggering a browser download by imperatively creating and clicking a DOM anchor element. The DOM-manipulation half — `document.createElement('a')`, `document.body.appendChild(a)`, `a.click()`, `a.remove()` — is baked directly into the same function that owns the zip-building logic. This means you can't unit-test the serialization-to-zip path without the test environment providing a real DOM, and you can't swap out the download mechanism (say, for a service-worker-based approach or a test spy) without rewriting the function. Recurring pattern — also observed in Tight Coupling — GitHub Actions Runtime Inside Business Logic in pattern-buddy/src/commentPoster.ts (PR #6); Tight Coupling — API Key Retrieval Inside Business Logic in pattern-buddy/src/claudeCaller.ts (PR #5). The theme is consistent: side-effectful infrastructure (DOM, GitHub Actions runtime, environment variables) gets folded into functions that should be pure or near-pure. Worth naming this as a codebase-wide habit to watch..
- **Implicit Global State Dependency (localStorage coupling)** in `src/lib/soulStack/storage.ts` (lines 1–29, PR #7): `loadStack`, `saveStack`, and `clearStack` reach directly into `localStorage` — a global singleton. This is fine for production, but it means any component or hook that calls these functions is implicitly coupled to the browser's storage layer. The Editor test already works around this by calling `localStorage.clear()` in `beforeEach`, which is a tell: the test has to know about the storage implementation detail in order to get a clean slate. If you ever want to test storage-related behaviour in a non-browser environment, or swap to IndexedDB or a different persistence strategy, every call site changes.
- **Tight Coupling — GitHub Actions Runtime Inside Business Logic (Partial Resolution)** in `pattern-buddy/src/anthropicClient.ts` (lines 1–21, PR #9): This is genuine progress on the recurring tight-coupling theme flagged in PRs #5 and #6. The API-key resolution and client construction have been lifted out of `callClaude` and `generateArchitectureMap` into a dedicated `createAnthropicClient` factory. That's a real improvement — the business-logic functions no longer reach into `core.getInput()` themselves for the API key. That said, `createAnthropicClient` still reaches directly into `core.getInput('anthropic-api-key')` and `process.env`, so the coupling hasn't been eliminated — it's been consolidated. The factory is still welded to the GitHub Actions runtime, which means tests still need `@actions/core` mocked or the env var set to get a client. That's meaningfully better than the coupling being spread across multiple modules, but it's worth naming where the boundary still sits. Recurring pattern — also observed in Tight Coupling — API Key Retrieval Inside Business Logic in pattern-buddy/src/claudeCaller.ts (PR #5); Tight Coupling — GitHub Actions Runtime Inside Business Logic in pattern-buddy/src/commentPoster.ts (PR #6).
- **Tight Coupling — GitHub Actions Runtime Inside commitFile (New Instance)** in `pattern-buddy/src/commitFile.ts` (lines 21–46, PR #9): The new `commitFile` utility is a genuinely good extraction — it eliminates the duplicated SHA-lookup-and-upsert logic that used to live in `mdUpdater.ts` and would have been copy-pasted into `architectureCommitter.ts`. But inside that utility, `github.getOctokit(core.getInput('github-token'))` is constructed directly, which is the same coupling pattern flagged across PRs #5 and #6. The function can't be called in a unit test without mocking `@actions/core` and `@actions/github`. This is a recurring codebase-wide habit: side-effectful infrastructure clients get constructed inside functions that should receive them as dependencies. Recurring pattern — also observed in Tight Coupling — API Key Retrieval Inside Business Logic in pattern-buddy/src/claudeCaller.ts (PR #5); Tight Coupling — GitHub Actions Runtime Inside Business Logic in pattern-buddy/src/commentPoster.ts (PR #6).
- **Tight Coupling — GitHub Actions Runtime Inside postArchitectureComment** in `pattern-buddy/src/architectureComment.ts` (lines 12–13, PR #9): Same pattern, new file. `postArchitectureComment` calls `github.getOctokit(core.getInput('github-token'))` inline, identical to the pattern previously flagged in `commentPoster.ts` (PR #6). At this point this is a codebase-wide structural habit rather than an isolated slip: every module that needs an Octokit client constructs it internally. The consequence is always the same — the function is untestable in isolation without mocking the Actions runtime. Recurring pattern — also observed in Tight Coupling — GitHub Actions Runtime Inside Business Logic in pattern-buddy/src/commentPoster.ts (PR #6); Tight Coupling — API Key Retrieval Inside Business Logic in pattern-buddy/src/claudeCaller.ts (PR #5).

## SOLID Violations
- **SOLID Violation - SRP (Single Responsibility)** in `pattern-buddy/src/mdUpdater.ts` (lines 1–74, PR #5): `mdUpdater.ts` is doing two distinct jobs: (1) mutating the local filesystem by writing the updated `.pattern-pointers.md` file, and (2) committing that file to GitHub via the Octokit API. These are separate responsibilities — local I/O and remote API interaction — bundled into a single module. If you ever want to test the file-mutation logic in isolation, or swap out the commit strategy, you're paying for both concerns at once.
- **SOLID Violation - SRP (Single Responsibility)** in `src/lib/soulStack/exportZip.ts` (lines 1–20, PR #7): This is the same SRP observation as the coupling issue above, but viewed through a different lens. `exportZip.ts` owns both 'produce the archive bytes' and 'deliver those bytes to the user's filesystem'. These are separate reasons to change: you might want to change the zip format or compression without touching the delivery mechanism, or change from a blob URL to a File System Access API write without touching the zip logic. The module currently conflates both. Recurring pattern — also observed in SOLID Violation - SRP (Single Responsibility) in pattern-buddy/src/mdUpdater.ts (lines 1–74, PR #5): filesystem mutation and GitHub commit logic bundled into one module. Same structural shape, different environment..
- **SRP Improvement — Config Extraction (Positive Refactor)** in `pattern-buddy/src/config.ts` (lines 1–50, PR #9): The config loading logic that previously lived inline inside `inputBuilder.ts` has been promoted to its own module with a typed `RawConfig` interface, a `DEFAULT_CONFIG` export, and proper handling of the new `architecture_map` section. This is a meaningful SRP improvement — `inputBuilder` no longer has to care about config schema parsing, and the config module now owns that responsibility entirely. The `RawConfig` interface is a particularly nice touch: it makes the on-disk snake_case shape explicit and keeps the type-casting honest.

## DRY Violations
- **DRY Violation — Section Header Map Duplication** in `pattern-buddy/src/mdUpdater.ts` (lines 14–23, PR #5): The `SECTION_HEADERS` map in `mdUpdater.ts` duplicates the section structure that also implicitly lives in `historyLoader.ts`'s `SECTION_KEYWORDS` and the `COLD_START_TEMPLATE` string. The canonical list of sections is spread across three places. Add a fourth section someday and you need to update all three.
- **DRY Violation — Duplicated Summary Builder Across Source and Dist** in `pattern-buddy/dist/index.js` (lines 40555–40566, PR #6): The `buildSummaryComment` function appears verbatim in both `src/commentPoster.ts` and `dist/index.js`. Now, this is the expected consequence of the committed build artifact pattern already flagged in PR #5 — the dist is a compiled copy of the source. It's not a DRY violation in the traditional sense (you're not maintaining two independent copies), but it's worth calling out as a concrete cost of the committed-dist trade-off: every logical change in source now shows up as two diffs (source + dist), and reviewers have to mentally skip the dist changes to focus on what actually matters. The new function makes this more visible. Recurring pattern — also observed in Committed Build Artifact Anti-Pattern in `.gitignore` (lines 8–14, PR #5).
- **Inline CSS String Concatenation for Conditional Classes** in `src/components/editor/JournalEditor.tsx` (lines 57–60, PR #7): The pattern of building className strings via template literals and `.trim()` — `\`sr-journal__item ${i === sel ? 'is-active' : ''}\`.trim()` — appears in at least a dozen places across the new components: `DemoReviewPanel`, `JournalEditor`, `SidePanel`, `Editor`, `Landing`, `SlideDots`, and more. It's not broken, but it's repeated boilerplate that's easy to get wrong (a missing space, a forgotten `.trim()`) and it makes conditional class logic harder to scan at a glance.
- **DRY Violation — Extracted & Shared (Positive Refactor)** in `pattern-buddy/src/extractJson.ts` (lines 1–25, PR #9): This is a lovely cleanup to celebrate. The `extractJson` utility that was previously duplicated — once inside `claudeCaller.ts` as `extractJSON` and effectively re-implemented for the architecture path — has been extracted into its own module. Both `callClaude` and `generateArchitectureMap` now import from a single source of truth. This is exactly the right move: one place to fix, one place to test, one place to extend when Claude inevitably starts wrapping its responses in yet another fencing style.

## Best Practices
- **Pipeline Pattern — Immutable Context Threading** in `pattern-buddy/src/index.ts` (lines 1–38, PR #5): The pipeline in `index.ts` threads an `AnalysisContext` object through each stage (`buildInput → loadHistory → callClaude → buildOutput → postComments → updateMD`), returning a new context at each step. This is a lovely immutable pipeline pattern — each stage receives the full context and returns an enriched copy. The intent is clear and the stages are nicely decoupled.
- **Committed Build Artifact Anti-Pattern** in `.gitignore` (lines 8–14, PR #5): The `.gitignore` is updated to explicitly un-ignore `pattern-buddy/dist/` so the compiled bundle can be committed. This is a known requirement for GitHub Actions (the runner needs a pre-built artifact), but it's worth documenting the trade-off: `dist/index.js` at 46,000+ lines is now part of your git history, making diffs noisy and the repo heavier over time. It also means the committed bundle can drift from the source if someone forgets to rebuild before pushing.
- **Implicit Type Casting — Unsafe `as unknown as`** in `pattern-buddy/src/inputBuilder.ts` (lines 50–55, PR #5): The diff response is cast with `as unknown as { data: string }` and later the repo content response with `as unknown as { data: { sha: string } }`. These double-casts bypass TypeScript's type safety entirely. They suggest the Octokit response types don't match the expected shape, but instead of understanding why, the types are being force-escaped.
- **Fallback / Graceful Degradation Pattern** in `pattern-buddy/src/commentPoster.ts` (lines 48–70, PR #6): This is a genuinely nice addition — wrapping the `createReview` call in a try/catch and falling back to a plain issue comment when inline reviews fail is a solid resilience pattern. GitHub's review API can be finicky (e.g. when the diff context is stale or the commit is no longer the HEAD), so having a fallback means PatternBuddy always surfaces its findings rather than silently dying. This is the Graceful Degradation pattern in action: attempt the preferred UX first, then step down to a simpler-but-reliable alternative.
- **Hardcoded Magic Index (array index used as stable key)** in `src/components/editor/JournalEditor.tsx` (lines 51–65, PR #7): The journal entry list uses the array index `i` as the React `key` prop (`key={i}`), and the `remove` function computes the new selection as `setSel(Math.max(0, i - 1))` based on position rather than identity. Using array indices as keys is harmless when the list is stable, but here the list is mutable — entries can be added, removed, and will eventually be reordered. React's reconciler uses the key to decide which DOM subtree to preserve; when an entry is deleted from the middle, every entry after it gets a new key and React will remount those rows unnecessarily (losing textarea focus/scroll state in the process).
- **Hardcoded Credential / Resource Identifier in Checked-in File** in `.claude/skills/deploy-azure/SKILL.md` (lines 1–91, PR #7): The SKILL.md file commits several pieces of identifying information that are typically kept out of source control or treated with care: the Azure subscription ID (`77d1db33-ff1f-4266-ba56-a3046d7280f7`), the account email (`yizyace@gmail.com`), the live hostname, the resource group name, and the Static Web App name. None of these are secrets — the deployment token is correctly handled via `gh secret set` — but subscription IDs and account emails committed to a public repo are routinely harvested by scanners looking for Azure targets, and they make phishing / social-engineering attacks marginally easier.
- **Strategy Pattern — Dual-Mode Dispatch** in `pattern-buddy/src/index.ts` (lines 48–83, PR #9): The `run()` function now dispatches between two distinct execution strategies — `runAnalysis` and `runArchitecture` — based on the `mode` input and the GitHub event payload. This is the Strategy pattern in action, and it's well-structured: each strategy is a named, self-contained async function rather than an inline block, which makes the dispatch logic readable and the individual passes independently testable. The guard for 'closed without merging' is also a nice touch — it avoids wasted API calls on a surprisingly common event.
- **Pipeline Pattern — Immutable Context Threading (Architecture Pass)** in `pattern-buddy/src/index.ts` (lines 48–65, PR #9): The new `runArchitecture` function follows the same immutable pipeline pattern already celebrated in the `runAnalysis` path from PR #5. `buildArchitectureInput` produces an `ArchitectureContext`, `generateArchitectureMap` returns an enriched copy with the architecture payload attached, and the downstream commit/comment steps receive the full context. The `{ ...context, architecture }` spread in `architectureMapper.ts` is idiomatic and consistent with how `AnalysisContext` is threaded through the analysis pipeline. Nice consistency.
- **Implicit Type Casting — Unsafe `as unknown as`** in `pattern-buddy/src/commitFile.ts` (lines 29–35, PR #9): The `as unknown as { data: { sha: string } }` double-cast is back, this time in the new `commitFile` utility. This is the same pattern flagged in `inputBuilder.ts` in PR #5 — the Octokit `getContent` response type doesn't match the expected shape, and instead of resolving the mismatch, the types are being force-escaped. In `commitFile` the cast is particularly worth addressing because this module is positioned as a shared infrastructure utility: any type unsafety here is inherited by every caller. Recurring pattern — also observed in Implicit Type Casting — Unsafe `as unknown as` in pattern-buddy/src/inputBuilder.ts (lines 50–55, PR #5).
- **Committed Build Artifact Anti-Pattern (Ongoing)** in `pattern-buddy/dist/index.js` (lines 40381–40381, PR #9): The committed `dist/index.js` bundle continues to grow — this PR adds several hundred lines of compiled output for the new architecture pipeline. This is the same trade-off flagged in PR #5: committing the bundle is a GitHub Actions requirement, but each PR that touches the source doubles the diff noise because both the TypeScript source and its compiled output change. The bundle is now substantially larger than the initial PR. Recurring pattern — also observed in Committed Build Artifact Anti-Pattern in .gitignore (PR #5).
